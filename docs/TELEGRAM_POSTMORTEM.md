# Telegram TestFlight: постмортем

Дата наблюдений: 4 августа 2026 года. Часовой пояс в этом документе — Europe/Moscow, если не указано иное.

## Итог

Монитор публичной страницы не является способом получить актуальный Telegram beta invite. На это есть две независимые причины:

1. по объявлению в сообществе Telegram приглашения теперь выдаёт `@TestFlightInvitesBot` подходящим активным участникам;
2. публичная HTML‑страница не является синхронным представлением account‑scoped состояния TestFlight и может расходиться между регионами десятки секунд.

Даже идеальный локальный `AXPress` не может создать eligibility, которого Apple backend не выдал аккаунту.

## Наблюдение №1

В 11:55:48 публичная Telegram‑страница дважды вернула `available`, после чего production pipeline запустился с `dry_run=false`. Старая реализация синхронно ждала завершения `/usr/bin/open` около 4,98 секунды. К началу AX‑поиска TestFlight уже показывал `beta_full`.

После этого deep‑link dispatch был сделан неблокирующим: локально он стал возвращать управление за 2–13 мс, а AX watcher запускался сразу.

## Наблюдение №2

Во втором событии исправленная автоматизация отработала так:

| Событие | Время |
|---|---:|
| Последний локальный ответ `beta_full` | 12:55:53.066 |
| Первый локальный HTTP `available` | 12:55:53.691 |
| Классификация `available` | 12:55:53.699 |
| Deep link отправлен LaunchServices | 12:55:53.728 |
| Второй HTTP подтвердил `available` | 12:55:54.012 |
| AX watcher запущен | 12:55:54.022 |
| TestFlight получил GURL | 12:55:54.364 |
| Account‑scoped join request начался | 12:55:54.398 |
| Account‑scoped ответ обработан | 12:55:55.744 |
| Публичный HTML вернулся в `beta_full` | 12:56:03.750 |

Deep link был отправлен через 29 мс после классификации, AX watcher — через 323 мс. Несмотря на это, TestFlight всё время показывал «мест больше нет» и не создавал `TestFlight.offerButton.accept`.

По внешнему наблюдению публичный checker сообщил об открытии примерно на 50 секунд раньше локального монитора. Локальные запросы в этот период:

- использовали уникальный query cache‑buster;
- получали текущий HTTP `Date` и уникальные correlation keys;
- попадали в один региональный кластер `daiquiri`;
- возвращали один и тот же `beta_full` body hash;
- содержали `Cache-Control: max-age=600`.

Это совместимо с региональной рассинхронизацией или задержкой snapshot на стороне Apple. Один только заголовок `Cache-Control` не доказывает, что конкретный ответ был отдан из локального cache, поэтому точная внутренняя причина не заявляется.

## Что доказано

- Python polling не спал 50 секунд: запросы выполнялись непрерывно и были response‑bound.
- После первого локального `available` задержка собственного pipeline измерялась миллисекундами.
- Публичный HTML оставался `available` около 10 секунд, пока авторизованный TestFlight показывал `beta_full`.
- Увеличение частоты запросов к тому же региональному представлению не устраняет рассинхронизацию.
- Обычный TLS proxy не дал безопасно исследовать содержимое account‑scoped запроса; pinning/trust bypass не применялся.

## Что не доказано

- Не установлено, был ли публичный `available` настоящим свободным first‑come slot или устаревшим/несогласованным snapshot.
- Не установлено, мог ли иной заранее одобренный Apple Account принять приглашение в тот момент.
- Не перехватывался и не воспроизводился приватный запрос принятия.

## Практический вывод

Для текущей Telegram‑схемы полезный поток выглядит иначе:

1. получить eligibility через официальный bot flow;
2. использовать тот же Apple ID, что авторизован в TestFlight;
3. дождаться персонального приглашения или появления сборки;
4. применять автоматизацию только для уведомления и быстрого открытия уже выданного приглашения.

Проект не автоматизирует активность в группе, взаимодействие с ботом или обход его решения.
