# Исследование частоты polling

Проверено 4 августа 2026 года для `https://testflight.apple.com/join/u6iogfd0`.

- Apple не публикует rate limit для публичных страниц `testflight.apple.com/join/*`.
- Документ Apple для авторизованного App Store Connect API описывает иной лимит по API key, сообщает его через `X-Rate-Limit` и приводит пример 3500 запросов за rolling hour. Этот лимит нельзя переносить на public join page: <https://developer.apple.com/documentation/appstoreconnectapi/identifying-rate-limits>.
- Public join page вернула `Server: daiquiri/5`, `Cache-Control: max-age=600`, gzip-body около 10,2 КБ и HTML около 42,6 КБ. `RateLimit`, `X-Rate-Limit` и `Retry-After` отсутствовали.
- Два запроса с одним и тем же cache-buster получили одинаковые `X-Apple-Jingle-Correlation-Key` и `Date`; уникальные query values получили уникальные correlation keys. Поэтому monitor использует уникальный cache-buster, иначе можно до 10 минут видеть один cache object.
- Отдельного status API в HTML нет. `HEAD` не возвращает состояние. Сервер игнорирует byte range для identity-body, но поддерживает его для gzip: `Range: bytes=0-3071` вернул HTTP 206 и ровно 3072 байта из полного gzip-body размером 10203 байта.
- Инкрементальная распаковка 3072-байтного gzip-префикса дала около 11,4 КБ начала HTML. В нём одновременно находятся title/app name, `showSteps`, `beta-status`, точный deep link, main/steps containers и app icon. Один и тот же parser корректно классифицировал реальный Telegram как `beta_full`, а реально доступную Kashikan (`Ssjq4DbX`) как `available`.
- Последовательный cold-connection тест: 20/20 HTTP 200, 1,61 запроса/с, median 603 мс.
- Последовательный keep-alive тест: 12/12 HTTP 200, 2,19 запроса/с, median 400 мс.
- Ограниченный burst: 45/45 HTTP 200 за 16,314 с, 2,76 запроса/с, median 347 мс; 429 и rate headers не появились.
- Контролируемая серия с постоянным HTTPS-соединением и целевым start interval 0,50 с: 15/15 HTTP 200 за 8,783 с, 1,71 запроса/с, median 459 мс, p95 941 мс, 15 уникальных correlation keys.
- Контролируемая серия с целевым start interval 0,25 с: 15/15 HTTP 200 за 6,341 с, 2,37 запроса/с, median 404 мс, p95 501 мс, 15 уникальных correlation keys. Поскольку запросы строго последовательны, фактический интервал стал response-bound — около 404 мс.
- После внедрения keep-alive рабочая реализация при настройке 0,55 с дала 12/12 HTTP 200/`beta_full`, median response 560 мс, p95 662 мс и median start gap 567 мс; все 12 correlation keys уникальны.
- Финальный production range-monitor наблюдался 132 check подряд за 83,735 с: 1,564 check/с, средний completion gap 639 мс, median network response 398 мс, p95 577 мс, все состояния `beta_full`, ни одного inconclusive range fallback.
- После настройки target 0,30 с с jitter ±0,05 с перезапущенный LaunchAgent дал 100/100 HTTP 206 без 429: mean response 373,8 мс, min 352 мс, max 780 мс. Из-за последовательного режима фактический темп в основном равен времени ответа, а не 3,33 запроса/с из конфигурации.

Короткие серии не доказывают безопасный суточный предел, а скрытый WAF может меняться. Точный порог 429 установить безопасным коротким тестом невозможно: его отсутствие означает только, что проверенные серии не были ограничены. После реального проигранного слота production target уменьшен до 0,25–0,35 с между стартами; клиент по-прежнему строго последовательный, поэтому при обычной задержке Apple 0,4–0,8 с фактическая частота остаётся response-bound. Он получает 3-КБ gzip-префикс и немедленно переходит на экспоненциальный backoff при HTTP 429, сетевой ошибке или любом неожиданном ответе. При `available` второй независимый range-check начинается сразу, но press gate открывается не раньше 300 мс; неоднозначный partial response автоматически подтверждается полным HTML. Проверка раз в миллисекунду потребовала бы около 1000 запросов/с, то есть примерно 86,4 млн запросов и сотни гигабайт трафика в сутки, поэтому она исключена.

Позднее внешний checker сообщил об `available` примерно на 50 секунд раньше локального endpoint. Локальный client всё это время непрерывно получал `beta_full` с текущими `Date`, уникальными correlation keys и cache-busters из одного регионального `daiquiri` cluster. Значит, более частый polling того же маршрута не гарантирует более свежий сигнал. Публичный пример конфигурации поэтому возвращён к консервативным 7 ± 1,5 секунды; быстрые значения остаются только зафиксированным экспериментом, а не рекомендацией.
